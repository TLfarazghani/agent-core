# Essential Commands (run from repo root; always use the venv interpreter)
- **Bootstrap (recommended):** `powershell -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1` — creates `.venv` (py -3.13 / fallback), installs requirements.txt, downloads the selected model's GGUF into `models\` (`-Model` = table alias, default 1.2B), fetches the pinned llama.cpp zip into `vendor\llama\` if missing, prints health-check summary. Switches: `-SkipModelDownload`, `-SkipLlamaDownload`, `-RunTests`; `-VenvDir` for a throwaway venv. Keep `bootstrap.ps1` pure ASCII (PS 5.1 reads BOM-less files as ANSI — non-ASCII breaks tokenization) and keep its model/ctx tables in sync with `windows/server_config.ps1`.
- **Create venv:** `py -3.13 -m venv .venv` — REQUIRED. `python` is 3.13.5 but system `pip` resolves to a 3.10 site-packages; never call bare `pip`.
- **Install:** `.venv\Scripts\python -m pip install -r requirements.txt` (pydantic, jsonschema, python-docx, python-pptx, docker, **openai v3 — in requirements since 2026-10-20, pinned `>=3.1,<4` because the orchestrator targets the v3 API shape — and huggingface-hub for the `hf` downloader**). Verified with a cold `bootstrap.ps1 -VenvDir <temp>` run (fresh venv + all deps install + import check pass).
- **Run all tests:** `.venv\Scripts\python -m pytest` collects every `test_*.py` (248 passed as of Phase 12); the JS-parity suites run separately via **Node**, not pytest: `node test_webgpu_engine.mjs` (engine+context+Phase-8/9/10/11/12 parity, 45 cases) and `test_parser_js.py` (spawns Node against `web/parser.js`, 4 cases). Node v22 is on PATH.
- **Model download:** `.venv\Scripts\hf.exe download LiquidAI/LFM2.5-1.2B-Instruct-GGUF LFM2.5-1.2B-Instruct-Q4_K_M.gguf --local-dir models`
  - huggingface-hub 1.x has **no `python -m huggingface_hub` module**; use `hf.exe`/`huggingface-cli.exe` in `.venv\Scripts`.
  - GGUF filename is capitalized `LFM2.5-1.2B-Instruct-Q4_K_M.gguf` — the lowercase name in Liquid docs is stale.
- **Start server:** `.\windows\server_config.ps1` (serves `127.0.0.1:8001`, model `LFM2.5-1.2B-Instruct`; `-Model LFM2.5-2.6B` / `LFM2.5-8B-A1B` / `$env:AGENT_CORE_MODEL` selects another table entry). Client-side, sessions for 2.6B also need `AGENT_CORE_MAX_CONTEXT_TOKENS=131072` and for 8B-A1B `=128000` (the default 32768 is fine for 1.2B).
- **One-click launch:** `Core-agent.bat` — starts llama-server if down, checks Docker, starts the web UI, opens `http://127.0.0.1:8002`
- **Run the agent (CLI):** `.venv\Scripts\python cli.py` (needs llama-server up + Docker Desktop for `run_code`). `MCP_BASE_URL` env opts in the networked tools.
- **Run the agent (Web UI):** `.venv\Scripts\python web\server.py [port]` (default 8002), then open `http://127.0.0.1:8002`. Talk to the browser app with `http://127.0.0.1:8002/api/health`.

# Architecture (non-obvious, do not violate)
- The loop, tool registry, state machine, and **approval gate** live in `core/` and are transport-agnostic. Platform code only adapts `AgentState → provider request` / `response → ToolCall[]`; it never re-implements the loop. UIs render `AgentState` and resolve approvals — see `docs/ui-ux-design.md`.
- `core/parser.py` must stay **stdlib-only** (`ast`-based Pythonic extraction, no `eval`). It is the cross-language contract ported line-for-line to `parser.js` / `AgentCore.kt`. Never add third-party imports. **Production-mileage caveat:** on the shipped Windows path, tool calls come from llama.cpp's structured OpenAI-style `tool_calls` JSON (via `--jinja`), so `parse_tool_calls` is currently exercised only by `web/engine.js` (WebGPU target) and by tests — it is the contract for the not-yet-shipped browser/Android paths, not a hot path on Windows today. Its "lenient" mode skips only syntax errors; semantic failures (positional args, `**kwargs`, non-literal values) raise `ParserError` — matching `web/parser.js`.
- Approval gate: `run_code` (and any `requires_approval` tool) halts via `state.pending_approval`, enforced **hardcoded in `core/tool_registry.dispatch()`** — never model-decided, never per-platform. `core/loop.resolve_approval(approved=bool)` is the only way through; only `approved=True` executes. **Multi-call turns:** when the model emits `[run_code, echo]` in one turn, the loop stashes the calls after the approval-gated one in `state.pending_calls` and resumes them after `resolve_approval` — do not "fix" this by dropping them. Args are validated **before** the approval gate (malformed calls never reach the human).
- **Security invariants:** `core/sessions.session_path()` rejects any session_id containing `/`, `\`, `:`, or `.`/`..` — the web server surfaces that as 400. `web/server.py` only accepts requests whose Host header (and Origin, when present) is a loopback address, and answers OPTIONS with 403 (no CORS headers) — this is the localhost-CSRF/DNS-rebinding defense; don't add CORS headers or weaken the check. `tools/_paths.unique_path()` claims filenames atomically with `O_CREAT|O_EXCL`.
- `AgentState`/`ChatMessage`/`ToolDefinition` are validated with pydantic against `schemas/*.json` before any tool runs. Tool args are also validated against each tool's `parameters` schema in `ToolRegistry.execute`.
- **Contract is snake_case, not OpenAI camelCase:** `ChatMessage` uses `content` (string), `function_calls[]`, `tool_call_id`. `windows/orchestrator.py` maps llama.cpp's camelCase `tool_calls` to this shape via `_from_openai_message` / `_to_openai_message`.
- Tool handlers are registered by name; `tools/registry.json` is loaded via `ToolRegistry.load_json(path, handlers)` where `handlers` maps tool name → `callable(arguments: dict) -> str`. State-aware handlers (the cognitive tools) are marked with `takes_state` and receive `(state, arguments)` via `execute(call, state)`.

# Phase 5 (built) — the cognitive layer: identity, memory, planning, reflection
Built and gate-passed (modules `core/meta.py`, `core/memory.py`, `core/planner.py`, `core/reflection.py` + `tools/cognitive.py`, JS ports `web/memory.js`/`web/planner.js`). Constraints that must hold when editing it:
- **Every core module is stdlib-only and transport-agnostic** (the `core/parser.py` / `core/context.py` precedent) and keeps a **JS-parity port** verified by `node test_webgpu_engine.mjs`. The web/Android targets re-use the same contract; never gate core logic on Windows.
- **Identity:** the agent's name is a single shared constant — **`AGENT_NAME` = "Agent Core"** — consumed by `cli.py`, `web/server.py`, and `web/worker.js`. `core/meta.py` `agent_bio(state, registry)` injects the identity block (name, **current date/time from the machine clock**, target, model, context budget, turn budget, live tool list) into the system prompt; `inspect_self` is a `requires_approval: false` tool returning a live snapshot. The `SYSTEM_PROMPT` tells the agent to answer "today"/date questions from that clock line and to use `web_search` for anything time-sensitive — never guess dates from memory. Resumed sessions get a fresh bio via `core/sessions.refresh_agent_bio` (web `get_session` + CLI `/resume`) so the clock value is never stale. JS mirrors live in `web/engine.js` + `web/worker.js` `BROWSER_TOOLS`.
- **Memory:** `core/memory.py` stores JSON at `~/.agent-core/memory/` mirroring `core/sessions.py`'s layout and **applies the same traversal guard on keys** (reject `/`, `\`, `:`, `.`/`..`). `remember`/`recall` are `requires_approval: false`; `new_agent_state()` seeds each session with a **bounded** recall that fits the Phase 6 context budget (newest-first, ~512 tokens).
- **Planning:** `AgentState.plan` is a pydantic field (`{goal, steps: [{id, description, status, result}]}`) — `core/state.py` **and** `schemas/agent_state.schema.json` (both are `additionalProperties/extra: forbid`) **and** `docs/data-contracts.md` must stay in sync; AGENTS.md requires docs/code sync on schema changes. `make_plan`/`update_plan` are `requires_approval: false`. **No plan-based approval bypass:** every step that calls a tool still hits the hardcoded gate in `core/tool_registry.dispatch()` independently.
- **Reflection/retry-once:** on a terminal turn, `core/loop.finalize_turn` writes a one-line lesson (`kind=lesson`) into memory when a tool failed or the user corrected the agent; bounded so it never blocks the loop. Retry-once: `state.retry_count` counts consecutive tool failures per user turn (reset in `step()` when the last message is a user message); past `RETRY_ONCE_LIMIT` (1) the loop gives up cleanly — still approval-gated for `run_code`; **never auto-retries a rejected call** (the `resolve_approval(approved=False)` path stays the only way through).
- **State-aware handlers:** cognitive tools receive the live `AgentState`; they are marked with `core.tool_registry.takes_state` and invoked as `handler(state, arguments)` from `ToolRegistry.execute(call, state=None)` (which stays backward-compatible for plain handlers — `test_runcode.py` calls `registry.execute(call)` with no state). JS tools set `stateful: true` and receive `(state, arguments)` in `web/engine.js`.
- **Tests:** `test_memory.py`, `test_planner.py`, `test_meta.py`, reflection/retry-once in `test_smoke.py`, JS parity in `test_webgpu_engine.mjs` (stateful tools, plan, retry-once, lesson). Each registry-filtered via `load_json(..., names={...})`.

# Phase 8 (built) — shared commands + permission modes
Constraints that must hold when editing it (patterns borrowed from the leaked `codeaashu/claude-code` source — **unlicensed, never copy code**):
- `core/commands.py` is the **only** command table: `COMMANDS` maps `{name, description, usage, handler}`; `CommandContext(state, registry, max_context_tokens, session_dir, memory_dir)` in, `CommandResult(text, state, quit, clear, error, save)` out. Both `cli.py` and `web/server.py` (`POST /api/sessions/<id>/command`, `GET /api/commands`) consume it — never re-implement a command in a UI. Browser mirror: `web/commands.js` (same shape, minus `/resume`/`/approve`/`/reject`/`/quit`, which are host-only).
- Permission modes are `AgentState.permission_mode` (`default|plan|auto|strict`) and are enforced **only** in `core/tool_registry._requires_approval()` via `dispatch()`. `HARDCODED_APPROVAL_TOOLS` (`run_code`) is checked **first**, so no mode bypasses it — only `resolve_approval(approved=True)` executes it. `plan` runs only `ToolDefinition.read_only` tools; `auto` skips the definition flag but not the hardcoded set; `strict` parks every call.
- The mode is a per-session setting: it serializes with the session, `POST /api/sessions` accepts `permission_mode`, `clear` preserves it, and the web sidebar selector (`#permission-mode`) plus `/mode` both change it. The JS mirror is `requiresApproval(tool, name, state)` in `web/engine.js` (`state=null` = legacy definition-flag behavior).
- Adding a tool: set `read_only: true` in `tools/registry.json` **and** in the `web/worker.js` `BROWSER_TOOLS` entry, otherwise `plan` mode will park it.
- Tests: `test_commands.py`, `test_permission_modes.py`, `/api/command` + per-session mode in `test_web.py`, and the Phase-8 cases in `test_webgpu_engine.mjs`.

# Phases 9–12 — Claude Code architecture review (all built)
Full spec, borrow/reject table, and ordering (`8 → 9 → 12 → 11 → 10`) live in `docs/plan.md` § "Phases 8–12". All five phases (8, 9, 10, 11, 12) exist and are tested — patterns only, **never** copy the unlicensed Claude Code source.

## Phase 9 (built 2026-10-19) — file & code-intelligence tools
Constraints that must hold when editing it:
- `tools/files.py` holds the six handlers; `tools/__init__.py` exports `FILE_TOOLS` + `register_files_tools(registry, root=None)` (called by `windows/orchestrator.py:default_registry()`). Each tool is in `tools/registry.json`. Tests filter with `names={...}` (see the registry-filtering gotcha below).
- Approval: `write_file`/`edit_file` set `"requires_approval": true`; `read_file`/`list_dir`/`glob`/`grep` are `false` **and** `read_only: true` (so `plan` mode may use them). **There is no default-deny** — `HARDCODED_APPROVAL_TOOLS` only special-cases `run_code`, so a new mutating tool must set the flag itself, in **both** `registry.json` and the `web/worker.js` `BROWSER_TOOLS` entry.
- Path safety: `AGENT_CORE_FILE_ROOT` (default repo root) is the allowed root. `resolve_path()` is **resolve-then-verify-contained** — it rejects bare-token style isn't used here (file paths legitimately contain separators), so it `resolve()`s and asserts the target stays under the root (symlink escapes included). `tools/_paths.unique_path()` (O_CREAT|O_EXCL) only claims brand-new output filenames, not arbitrary edits.
- `edit_file` replaces exactly one occurrence and fails when `old_string` is absent or non-unique; every write is atomic (temp file + `os.replace`) so a partial write never lands. `read_file`/`grep` are bounded; `glob` rejects absolute patterns and `..`.
- Web parity: the browser cannot touch arbitrary host paths, so `BROWSER_TOOLS` proxies the six tools through `POST /api/file` (`web/server.py` `_file_dispatch`, loopback/CSRF-guarded). The endpoint refuses `write_file`/`edit_file` unless the body carries `approved: true`, which `web/worker.js` only sends inside `run` (after the browser engine's own gate). Documented ceiling: host files only, under the server's file root.
- Tests: `test_files.py` over a `tempfile` root (no live deps) — read/edit round-trip, absent + non-unique `old_string`, out-of-root/traversal rejection, and that `write_file`/`edit_file` halt at the gate; `/api/file` in `test_web.py`; `test_phase9_file_tool_flags_parity` in `test_webgpu_engine.mjs`.

## Phase 10 (built 2026-10-19) — bounded sub-agents + skills
- `core/subagent.py`: `spawn_subagent(parent_state, goal, provider, registry, max_turns=MAX_SUBAGENT_TURNS, memory_dir=None) -> SubagentResult` runs a nested `core.loop.run`. `MAX_SUBAGENT_TURNS=4`, `MAX_CONCURRENT_SUBAGENTS=1`; the child is marked `active_subagents=1` so a nested `agent` call is **refused** (one level deep). Returns `status` `ok|needs_approval|rejected`.
- **The approval gate is never bypassed:** a gated tool inside the child stops the child and returns the pending call; the `agent` tool sets `parent_state.pending_approval` and `core/loop.step` breaks (keeping the rest in `pending_calls`) so the human resolves it. `resolve_approval(approved=True)` is still the only executor.
- `tools/subagent.py` (`AGENT_TOOLS={"agent"}`, `register_subagent_tool`) is **transport-registered** (`cli.py`, `web/server.py`) because it needs a provider — not in `default_registry()`.
- `tools/skills.py` (`run_skill`, `list_skills`; skills are `skills/*.json` = `{name, description, prompt, tools?}`). `run_skill` sets `state.tool_allowlist` and injects the prompt. The allowlist is enforced as a **denial** in `core/tool_registry.dispatch()` and cleared at the next user turn in `step()` — it is a restriction, never an approval bypass.
- JS ports: `web/subagent.js`, `web/skills.js`; `web/engine.js` mirrors the allowlist denial and clears `tool_allowlist` per turn; `web/worker.js` exposes `agent`/`run_skill`/`list_skills` and proxies skills via `GET /api/skills`.
- Tests: `test_subagent.py`, `test_skills.py`, the `agent`/`/api/skills` cases in `test_web.py`, and the Phase-10 cases in `test_webgpu_engine.mjs`.

## Phase 11 (built 2026-10-19) — compaction, memory extraction, tasks
- Compaction: `core/context.py` `should_compact(messages, budget)` + `compact_to_budget(messages, budget, summarize)` splice one `"Summary of earlier conversation:"` system message in place of the dropped turns (after the system prefix). `trim_to_budget` already guarantees the live turn is never dropped and tool/assistant pairs never split. Opt-in in `windows/orchestrator.LlamaCppProvider` via `compaction=True` / `AGENT_CORE_COMPACT=1`; `_summarize` is a guarded (non-recursive) non-streaming generate that never raises. JS port `web/context.js` `shouldCompact`/`compactToBudget`.
- Memory extraction: `core/reflection.extract_memories(state, provider=None, limit=5, memory_dir=None)` — heuristic by default (no extra model turn), model-based when a provider is passed; bounded and **deduped by key** so re-running is idempotent. Called from `finalize_turn` (never raises).
- Tasks: `core/tasks.py` (`create_task`/`update_task`/`list_tasks`/`render_tasks`, `VALID_TASK_STATUSES`) + `AgentState.tasks: list[Task]` (distinct from `plan`). Tools `task_create`/`task_update`/`task_list` (`read_only: true`, no approval) and the shared `/tasks` command (`/tasks`, `/tasks add <text>`, `/tasks task_N <status>`). Serializes with the session. JS port `web/tasks.js` + `/tasks` in `web/commands.js`.
- Tests: `test_tasks.py`, compaction cases in `test_context.py`, extraction cases in `test_memory.py`, the compaction case in `test_orchestrator.py`, and the Phase-11 cases in `test_webgpu_engine.mjs`.

## Phase 12 (built 2026-10-20) — observability: usage telemetry + doctor
- `core/telemetry.py` (stdlib-only, **local-only — no network**): `record_usage(state, usage, latency_s=None)` appends one `TurnUsage` record to `AgentState.usage` per provider generate (server-reported tokens + generation latency + epoch timestamp; never raises); `session_usage(state)` folds records into `{turns, prompt_tokens, completion_tokens, total_tokens, generate_seconds, tokens_per_second, last_tokens_per_second}`; `format_cost` renders `/cost` (tokens-only, always "$0.00 — local"); `format_doctor` renders `/doctor`.
- `AgentState.usage: list[TurnUsage]` is live in `core/state.py` **and** `schemas/agent_state.schema.json` **and** `docs/data-contracts.md` (all three must stay in sync; additionalProperties/extra forbid). It serializes with the session, so usage survives CLI ↔ web resumes. `windows/orchestrator.LlamaCppProvider` calls `record_usage(state, ...)` after every generate (streaming with `include_usage` from Phase 4, and non-streaming); the canonical `DEFAULT_SERVER_URL = "http://127.0.0.1:8001/v1"` now lives in `core/telemetry.py` and `windows/orchestrator.DEFAULT_BASE_URL` re-exports it.
- Commands: `/cost` (session tokens); `/context` keeps the Phase-6 budget line and adds a "Real usage (server-reported)" line when usage exists. JS mirror: `web/telemetry.js` (`sessionUsage`/`formatTokens`/`formatCost`) + `/cost` in `web/commands.js`; `newState()` in `web/engine.js` seeds `usage: []`. Browser ceiling: Transformers.js does not surface usage, so in-browser `state.usage` stays empty — the sidebar readout falls back to the chars/4 estimate.
- `/doctor` in `core/commands.py` calls `run_doctor(state, base_url=ctx.server_base_url, ..., probes=ctx.doctor_probes)` — probes: llama-server `/health`, `/v1/models` model match vs `AgentState.model`, client budget vs `EXPECTED_CTX_BY_MODEL` (mirrors the `windows/server_config.ps1` ctx table), Docker availability (`docker info`, injectable), and session/memory dir writability. **Every probe is injectable** (`CommandContext.doctor_probes`; `check_llama_server`/`check_model_match` take `urlopen=`, `check_docker` takes `probe=`, tests pass `tempfile` dirs) — never probe the real network or daemon from a test. `/doctor` is host-only: no browser `web/commands.js` entry (the web UI runs it server-side via `POST /api/sessions/<id>/command`; `AgentApp(doctor_probes=...)` injects fakes in `test_web.py`).

# Toolchain gotchas
- **llama.cpp:** prebuilt cu12.4 binary in `vendor\llama\` (works on the CUDA 12.9 driver). No cmake/MSVC on this machine — never build from source. The **`--jinja` flag is mandatory** for OpenAI-shaped `tool_calls`.
- **Never use Ollama** for this GGUF — older syncs throw `missing tensor 'output_norm'`. Use the direct llama.cpp binary + direct HF download.
- **openai is v3** (3.1.0): the v1 `client.chat.completions` API shape in the research docs is outdated; the orchestrator must target the v3 client API.
- `.venv/`, `models/`, `vendor/` are gitignored — binaries/weights are never committed. Repo is a git repo (commits exist); keep docs/code in sync when schemas change.

# Testing quirks
- `test_smoke.py` is deliberately one self-contained file with `assert`-based tests and a `main()` runner; it proves the approval gate (ordinary call executes, `run_code` halts, rejection clears without executing). It runs without pytest installed. Keep this property.
- `test_networked_tools.py` (Phase 1) runs the same way and spins up a stdlib `http.server` mock MCP-remote — no real network, no external services. It covers `send_email` (MCP transport, approval-gated) and `send_message` — `web_search` moved to local `test_web_search.py`, and native-SMTP `send_email` lives in `test_email.py`.
- `test_email.py` (native SMTP email) is self-contained: a recording `FakeSMTP` connection as the injectable `smtp_factory` and a dict-returning callable as the injectable `settings` — never a live SMTP server or the real environment. Never construct `smtplib.SMTP` at import time in `tools/email.py` (same rule as run_code's docker client).
- `test_web_search.py` (Phase 1b) uses a **fake `urlopen`** — no network. `tools/web_search.py` has an injectable `urlopen` param (same pattern as run_code's injectable docker client); never hardcode the real opener into tests. Do not make web-search tests require live DDG/Google/Wikipedia.
- `test_docgen_tools.py` (Phase 2) writes real .docx/.pptx to a `tempfile` dir and reopens them with python-docx/python-pptx to verify content. Output dir defaults to `output/` (override `AGENT_CORE_OUTPUT_DIR`); it is gitignored via `output/` — check `.gitignore` if you add generated artifacts.
- `test_runcode.py` (Phase 3) uses a **fake docker client** — no daemon needed. `tools/run_code.py` has an injectable `client` param; never change it to construct `docker.from_env()` at import time. Timeout uses a watchdog thread that kills the container.
- `test_files.py` (Phase 9) is a self-contained file (like `test_smoke.py`) using a `tempfile` root via `register_files_tools(registry, root=...)` — never the real repo root. `tools/files.py` handlers take an injectable `root`; keep it that way so tests never touch live files.
- `test_subagent.py` / `test_skills.py` (Phase 10) and `test_tasks.py` (Phase 11) are self-contained (fake providers; a `tempfile` skills dir / session dir) — no model, no Docker. `tools/subagent.py` takes an injectable `provider_factory`; `tools/skills.py` takes an injectable `skills_dir`.
- `test_orchestrator.py` (Phase 4) stubs the OpenAI client — no server needed. `windows/orchestrator.py` imports `openai` (v3); it has been in `requirements.txt` since 2026-10-20.
- `test_web.py` (web UI) starts the real `web/server.py` on an ephemeral port with a **fake provider + fake registry** — no llama-server, no Docker. It exercises the actual HTTP + SSE + loop + approval plumbing. Do not let web/server tests require a live model.
- `web/server.py` inserts the repo root into `sys.path` itself (it runs from the `web/` directory, so `core` is not otherwise importable). It binds `127.0.0.1` only.
- **run_code needs Docker Desktop running** for real use (`docker info` must succeed). The Python sandbox also needs the `python:3.12-slim` image pulled on first use (same for `node:20-slim`, `bash:5`).
- Sessions (CLI and web) serialize `AgentState` to `~/.agent-core/sessions/*.json` via `core/sessions.py` — a session started in the CLI can be resumed in the web UI and vice versa. `SYSTEM_PROMPT` lives there too; both UIs seed new sessions with it. **`max_turns` is a per-session setting** (default 8, `AGENT_CORE_MAX_TURNS` env var for new sessions; web sidebar "turn budget" input / CLI `/turns <n>` override at create/clear) and serializes with the session, so a resumed session keeps its budget.
- Each test file filters `tools/registry.json` to its own tools via `load_json(..., names={...})`. Adding a tool to `registry.json` will break other suites unless they pass `names=`.
